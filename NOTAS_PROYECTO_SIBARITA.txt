--------------------------------------------------
1. DE QUE TRATA EL PROYECTO
--------------------------------------------------
Sibarita es un sistema web de gestion de inventario y logistica
multi-almacen. Gestiona 3 almacenes (MALSA, JOPISA, INDELPAS).

Funcionalidades principales:
- Autenticacion con roles: admin, supervisor, operador, auditor,
  transportista (login con JWT).
- Inventario: stock por almacen y producto, tipo NUEVO / DEVOLUCION.
- Movimientos: transferencias de producto entre almacenes (origen -> destino),
  con cantidad, tipo, usuario responsable y fecha.
- Almacenes: alta y consulta de almacenes y su ubicacion.
- Usuarios: administracion de usuarios, rol y almacen asignado (solo admin).
- Alertas: notificaciones (ej. stock bajo).
- Reportes / Historial: consulta y exportacion a PDF (jspdf + jspdf-autotable),
  graficos con recharts en el Dashboard.
- Logs: auditoria de acciones (logMiddleware).
- Control de acceso por ruta y por rol en el frontend (RutaProtegida).

--------------------------------------------------
2. STACK TECNICO
--------------------------------------------------
BACKEND (backend/):
- Node.js + Express 5
- PostgreSQL (via pg), esquema en src/config/database.sql
  (tablas: roles, almacenes, usuarios, productos, inventario, movimientos)
- Autenticacion JWT (jsonwebtoken) + bcryptjs para passwords
- Estructura por capas: routes/, controllers/, middlewares/ (auth y log), config/
- cors, dotenv
- Deploy: RESUELTO (21/08) -> Render. Backend real corriendo en
  https://sibarita-almacen.onrender.com (ver seccion 5 para detalle
  completo: base de datos, variables de entorno, fecha de vencimiento).
  railway.toml se puede borrar si no se usa Railway (quedo como opcion
  de respaldo, sin backend desplegado ahi).

FRONTEND (frontend/):
- React 19 + Vite 8
- React Router v7 (rutas protegidas por rol)
- Tailwind CSS v4
- Axios (utils/api.js)
- Recharts (graficos del Dashboard)
- jsPDF + jspdf-autotable (exportar reportes PDF)
- Context API (AuthContext) para sesion/usuario
- TypeScript configurado, pero paginas en .jsx
- Deploy: Vercel (vercel.json, carpeta .vercel/)

Resumen: app full-stack React + Express + PostgreSQL tipo WMS ligero,
con control de acceso por roles. Frontend en Vercel
(https://sibarita-almacen.vercel.app), backend en Render
(https://sibarita-almacen.onrender.com). Ver seccion 5 para el detalle
completo del deploy.

Decisiones tomadas (regla de negocio de cada punto):

  producto en el CATALOGO (no por linea, no por guia). "EN PARTIDA"
  abre una sub-tabla de partidas parciales (cantidad + referencia) que
  suman la cantidad total de la linea. "ENTERO" = comportamiento actual.
- EDITAR GUIA CERRADA (Bloque 2): en estado CERRADA solo se puede
  cambiar la CANTIDAD de las lineas y el NUMERO DE O.C. Nada mas.
- STOCK CONSOLIDADO POR MOTIVO (Bloque 3): es un REPORTE de salidas
  agrupadas por motivo (uso interno / prestamo / reparacion / desecho /
  otro), por almacen y periodo. No es marcar el inventario con motivo.
- "CODIGO NUEVO EN NOMBRE USADO" (Bloque 3): NO es requerimiento aparte,
  es lo mismo que la devolucion "Usado" del Bloque 4.
- "PARAMETROS DE STOCK A 10 DIAS" (Bloque 3): es una ALERTA DE STOCK
  SIN MOVIMIENTO -> etiquetas/productos con 10+ dias en almacen sin
  salir.
- DEVOLUCION "USADO" (Bloque 4): el item devuelto a Mesa marcado como
  usado REINGRESA al inventario con una ETIQUETA/CODIGO NUEVO (marcado
  usado, separado del stock nuevo) PERO SI cuenta para el stock
  consolidado. Nota de devolucion imprimible, ingreso por unidad.
- COMPRAS DIARIAS (Bloque 5): MODULO NUEVO APARTE (fecha, oficina,
  proveedor, montos), ligado OPCIONALMENTE a una Solicitud de
  Materiales. No es extension del modulo actual ni un reporte.
- SERVICIOS (Bloque 6): guia o linea de TIPO "SERVICIO" -> se registra
  e imprime, NO genera etiqueta ni toca inventario.
- STOCK EN ORDEN DE SALIDA (Bloque 7): mostrar LOS DOS -> total
  agregado por producto + conteo de etiquetas individuales disponibles.
- "QUE LOS PRODUCTOS NO SE CRUCEN" (Bloque 7): control de CONCURRENCIA
  sobre la MISMA ETIQUETA (bloquear/avisar si dos operaciones tocan el
  mismo codigo a la vez).

  advertencia, no romper el flujo actual. NADA que construir.

- CONCURRENCIA - RECOMENDACIONES DE LA PRUEBA DE ESTRES APLICADAS (02/09).
  Tras la prueba de concurrencia del 02/09 (arriba) se aplicaron 3
  cambios de codigo para que un pico de peticiones no tumbe el backend:
  * backend/src/config/db.js (Recomendacion 1): el Pool de pg usaba los
    valores por defecto (max 10, sin timeouts) y un pico de peticiones
    concurrentes lo dejaba tildado para siempre. Ahora: max 20,
    connectionTimeoutMillis 5000 (la peticion falla claro si en 5s no hay
    conexion libre, en vez de colgarse), idleTimeoutMillis 30000,
    statement_timeout 20000 (Postgres aborta consultas > 20s),
    lock_timeout 8000 (aborta una consulta que lleve 8s esperando un
    candado -> rompe el cuello de botella cuando varias guias tocan el
    mismo producto/inventario a la vez), idle_in_transaction_session_
    timeout 15000 (corta transacciones abandonadas). Ademas pool.on
    ('error') para que un error en una conexion ociosa no tumbe el
    proceso, y se libera el client de la conexion de prueba del arranque.
  * backend/src/routes/guias.js (Recomendaciones 2 y 3): el find-or-create
    del producto cuando la linea trae nombre libre (no producto_id) se
    movio a un PRE-PASS en AUTOCOMMIT, antes de abrir la transaccion de la
    guia. Antes se hacia dentro de la transaccion y el candado del
    producto nuevo quedaba tomado durante TODA la transaccion; con muchas
    guias concurrentes sobre el mismo producto nuevo eso serializaba todo
    y caia el backend. En autocommit el candado dura milisegundos. El
    bloque !productoId dentro de la transaccion queda solo como red de
    seguridad (usa it.__metrica ya resuelto). Si la guia falla despues
    puede quedar un producto de catalogo sin stock: es inocuo
    (producto_canon lo deduplica) y un reintento lo reutiliza.
