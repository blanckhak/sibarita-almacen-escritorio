FASE 7 - Metrica de producto (ENTERO / EN_PARTIDA) + partidas parciales
======================================================================
Fecha: 28/08/2026

REGLA DE NEGOCIO (definida en Fase 3)
------------------------------------
- La "metrica" es un atributo FIJO del producto, se define EN EL CATALOGO
  (no por linea ni por guia). Valores:
  * ENTERO     -> comportamiento actual: se ingresa una cantidad directa.
  * EN_PARTIDA -> al cargar ese producto en una linea de guia se abre una
    sub-tabla de "partidas parciales" (cantidad + referencia/paquete).
    La suma de las partidas ES la cantidad total de la linea
    (ej. 12 + 8 = 20). No pidio lote ni vencimiento, solo el desglose.
- Editar guia CERRADA (cantidad / N de O.C.) es Fase 8, NO se toco aca.

CAMBIOS DE ESQUEMA (migraciones idempotentes en setup.js + database.sql)
----------------------------------------------------------------------
- productos + columna metrica VARCHAR(10) NOT NULL DEFAULT 'ENTERO'
  CHECK (metrica IN ('ENTERO','EN_PARTIDA')). CHECK con nombre propio,
  recreado con DROP/ADD (idempotente).
- Tabla nueva guia_item_partidas (id, guia_item_id FK, cantidad, referencia).
Ninguna migracion borra datos. Ya aplicadas en sibarita_db local.

BACKEND
-------
- routes/productos.js: POST y PUT aceptan `metrica` (validada contra
  ['ENTERO','EN_PARTIDA'], default ENTERO). GET ya la devuelve (SELECT p.*).
- routes/guias.js POST /:
  * cada item puede traer `partidas: [{cantidad, referencia}]` y, para
    producto nuevo dado de alta desde la guia, `metrica`.
  * la metrica REAL se resuelve dentro de la transaccion (del catalogo si
    el producto existe; del form si es nuevo). Para un producto EN_PARTIDA:
    - si no hay partidas -> 400 con ROLLBACK.
    - la cantidad de la linea se DERIVA de la suma de partidas (fuente
      unica de verdad; se ignora it.cantidad que mande el cliente).
    - se insertan las filas en guia_item_partidas despues del guia_item.
  * producto ENTERO: ignora cualquier `partidas` que llegue.
  * validacion pre-transaccion: cada partida con cantidad > 0; si la linea
    trae partidas no se exige el campo cantidad.
- routes/guias.js GET /:id: el detalle de items trae `producto_metrica` y
  un array `partidas` por linea (query aparte a guia_item_partidas,
  agrupada por guia_item_id).

FRONTEND

- pages/Productos.jsx: select "Metrica" en el form (Entero / En partida)
  con nota explicativa, columna "Metrica" en la tabla (badge indigo para
  "En partida"), y en el export Excel/PDF.
- pages/Guias.jsx (Nuevo Ingreso):
  * cada linea arranca metrica ENTERO / partidas [].
  * al elegir un producto del catalogo se copia su metrica; si es
    EN_PARTIDA aparece el editor de partidas (filas cantidad + referencia,
    "+ Agregar partida", quitar) y el campo Cantidad pasa a solo-lectura
    mostrando la suma ("suma de partidas").
  * producto nuevo inline: select de metrica al vuelo (se crea en el
    catalogo con esa metrica).
  * submit: envia `partidas` (solo EN_PARTIDA) y `metrica` (productos
    nuevos); cantidad = suma de partidas. Guarda contra enviar una linea
    "en partida" sin partidas validas.
- pages/GuiaDetalle.jsx: en la tabla de items y en la vista de impresion
  "Nota de Ingreso", las lineas EN_PARTIDA muestran badge "EN PARTIDA" y
  el desglose de partidas bajo el nombre del producto.

/CODE-REVIEW (medium, 28/08) - 1 hallazgo, corregido
---------------------------------------------------
1. Las cantidades de partida (y la cantidad de linea ENTERO) solo se
   validaban como > 0, nunca como enteras, pero guia_items.cantidad y
   guia_item_partidas.cantidad son columnas INTEGER -> una cantidad
   decimal ("1.5") pasaba las validaciones y reventaba con un error
   crudo de Postgres devuelto como 500.
   -> guias.js: helper esEnteroPositivo(v) (Number.isInteger + > 0),
      usado en la validacion pre-transaccion de partidas y de cantidad,
      y en el chequeo dentro de la transaccion. Se endurecio de paso el
      camino ENTERO que ya existia (mismo hueco latente).
   -> Guias.jsx: input de partida con step="1"; el guard de submit ahora
      rechaza partidas no enteras / <= 0 / linea sin partidas validas.
   Re-probado (test-fase7.mjs, 16/16 OK): partida decimal -> 400 limpio,
   linea ENTERO decimal -> 400 limpio. Build de frontend limpio.
